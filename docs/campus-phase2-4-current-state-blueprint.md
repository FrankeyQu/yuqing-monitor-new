# 校园舆情二至四阶段现状融合实施蓝图

> 本蓝图用于指导现有系统后续演进。爬虫、自研采集平台、登录态采集、代理池和平台逆向能力单独立项，不纳入本文实施范围。

## 1. 背景与边界

当前系统已经不是从 0 开始建设。后端和前端已经具备数据接入、监测命中、线索研判、预警、事件处置、报告生成等骨架能力，后续重点不是新建平行模块，而是在现有模块上补齐规则体系、状态约束、结构化依据和跨模块体验。

本阶段继续沿用现有采集模式：

- `baidu_search`：公开网页和新闻发现，可选 Jina Reader 正文增强。
- `third_party_api + provider=tikhub`：抖音、小红书、快手等高难平台补充，以及现存微博、B站、知乎、微信公众号接入兼容。
- `public_web_pull`：白名单公开网页单 URL 读取。
- `manual`：人工录入线索和事件台账。

本阶段不做：

- 自研全平台爬虫。
- 登录态采集、Cookie/Token/签名参数保存。
- 代理池、账号池、验证码绕过。
- 大规模评论采集。
- Controller 绕过 Service 直接拼接跨模块数据。

## 2. 现有系统盘点

### 2.1 已有业务链路

现有链路已经基本成型：

```text
campus_ingest_record
  -> campus_monitor_result
  -> campus_clue
  -> campus_alert
  -> campus_event
  -> campus_disposal_task / campus_disposal_record
  -> campus_report
```

该链路需要继续坚持以下边界：

- 接入记录只表示采集到了公开内容。
- 监测命中只表示规则扫描命中。
- 线索表示经过人工或规则筛选、值得研判和复用的数据。
- 预警表示需要关注、响应或升级的风险信号。
- 事件表示需要组织处置、派单和归档的业务对象。
- 报告只能面向线索、预警、事件和处置结果，不应直接把未研判的宽泛接入记录写入报告。

### 2.2 模块现状表

| 模块 | 当前已有能力 | 主要缺口 | 后续定位 |
| --- | --- | --- | --- |
| `campus_ingest` | 百度、TikHub、Jina Reader、公开网页白名单、接入记录、运行日志、调用日志 | 采集成本治理和公开网页底座单独立项；本阶段只复用现有接入结果 | 负责原始数据来源，不负责业务定性 |
| `campus_monitor` | 任务、自动接入编排、监测命中、统一监测信息、转线索、转预警、忽略、重点目标 | 学校相关性字段缺失；主题分类弱；风险解释不够结构化 | 从“扫到”升级为“命中质量可解释” |
| `campus_clue` | 线索列表、详情、人工研判、归档、操作日志、转事件状态 | 线索主题、相关性、风险依据缺少统一字段；批量研判仍偏操作层 | 承接有效线索和人工研判结论 |
| `campus_alert` | 敏感词、规则、线索触发预警、账号内容触发预警、处理/忽略 | 预警依据只有 `matchedKeywords`，缺少结构化 evidence；风险等级口径需统一 | 负责风险信号和响应入口 |
| `campus_event` | 线索转事件、定级、派单、反馈、退回、复核、归档、事件-线索关系 | 状态前置校验需强化；相似线索聚合不足；SLA/超时提醒弱 | 负责处置闭环和事件台账 |
| `campus_report` | 模板、报告保存、传统生成、AI 生成、SSE、Word/PPT 下载 | 治理复盘指标不足；报告数据源和事件处置记录绑定需增强 | 从“生成报告”升级为“治理复盘” |
| `campus_ai` | 供应商、模型、功能绑定、提示词、调用日志，已接入报告/研判/词云/接入配置 | AI 输出与人工确认边界需要继续固化 | 辅助摘要、分类、研判建议和报告，不替代人工定性 |

## 3. 统一基础口径

### 3.1 风险等级先沿用现有枚举

当前代码和前端已经使用 `normal / concern / major / urgent`。为减少迁移成本，二至四阶段不再引入新的 `warning / critical` 代码值，统一采用：

| 代码值 | 展示名称 | 业务含义 |
| --- | --- | --- |
| `normal` | 普通关注 | 与学校相关但暂不需要预警响应 |
| `concern` | 一般预警 | 存在负面或风险信号，需要研判关注 |
| `major` | 重大预警 | 涉及重点风险主题、传播扩散或需要部门响应 |
| `urgent` | 特别重大 | 涉及人身安全、群体性、重大舆论扩散或应急事件 |

后续所有模块必须使用同一套代码值：

- `campus_monitor_result.risk_level`
- `campus_clue.risk_level`
- `campus_alert.risk_level`
- `campus_event.risk_level`
- 报告模板变量和前端标签展示

### 3.2 主题分类建议先用固定字典

第一版不追求复杂模型，先用校园业务字典：

| 主题代码 | 主题名称 |
| --- | --- |
| `food_safety` | 食品安全 |
| `dormitory` | 宿舍管理 |
| `campus_safety` | 校园安全 |
| `bullying_conflict` | 欺凌冲突 |
| `teacher_ethics` | 师德师风 |
| `fee_dispute` | 收费争议 |
| `admission_employment` | 招生就业 |
| `exam_teaching` | 考试教学 |
| `logistics_service` | 后勤服务 |
| `public_incident` | 公共事件 |
| `rumor` | 谣言不实信息 |
| `other` | 其他 |

落地策略：

- 事件层已有 `eventType`，优先对齐该字段。
- 线索和监测结果后续补 `topicCategory` 或等价字段。
- 前端先按字典展示，AI 分类只能作为建议，最终仍允许人工调整。

### 3.3 状态机继续沿用现有文档

现有 `docs/STATE_MACHINE.md` 已定义：

- 线索：`pending_judge -> judged -> converted / archived`
- 事件：`pending_judge -> rated -> assigned -> feedback -> reviewed -> archived`
- 处置任务：`pending -> completed -> returned / confirmed`
- 预警：`pending -> handled / ignored`
- 报告：`draft -> generated -> archived`

后续实施只补状态前置校验，不重新发明一套状态。

## 4. 阶段二：研判与预警增强

阶段目标：让系统从“采到/扫到信息”升级为“能解释为什么相关、为什么有风险”。

### 4.1 P2-1 风险和主题字典统一

现状：

- 风险等级在多个页面和服务中已有实现，但展示文案不完全一致。
- 主题分类主要体现在事件 `eventType` 和前端统计中，尚未形成统一字典。

改造点：

- 固化风险等级 `normal / concern / major / urgent`。
- 新增或补齐校园主题字典。
- 统一前端风险标签、筛选项和报告模板变量。
- 更新 `STATE_MACHINE.md`、`API_CONTRACT.md`、`TEST_CHECKLIST.md` 中风险等级说明。

涉及范围：

- 后端：`CampusAlertServiceImpl`、`CampusMonitorServiceImpl`、`CampusClueServiceImpl`、`CampusEventServiceImpl` 中风险等级默认值和校验。
- 前端：`MonitorView.vue`、`JudgmentView.vue`、`AlertView.vue`、`EventView.vue`、`ReportView.vue`。
- 文档：`docs/STATE_MACHINE.md`、`docs/API_CONTRACT.md`、`docs/TEST_CHECKLIST.md`。

验收标准：

- 全系统风险等级代码值一致。
- 前端不再出现同一风险等级多套文案。
- 报告、线索、预警、事件筛选项一致。

Batch40 当前落地：

- 新增校园业务风险等级收口枚举，线索、事件、预警、监测、接入、账号动态和检测命中写入时统一校验或归一。
- 新增前端统一风险等级配置，监测、研判、预警、事件、接入、检测、账号、工作台、态势和分析页面复用同一套标签。
- 新增 `risk_level` 字典修正和 `campus_event_topic` 主题字典种子；旧 `higher` 字典项停用，服务端继续兼容并映射到 `major`。

### 4.2 P2-2 学校相关性判断

现状：

- 监测任务已有主体词、别名、关键词、负面词。
- 监测命中已经收紧为“主体词/别名 + 有效关键词或负面/风险词”。
- 实体层尚未有明确的学校相关性评分和解释字段。

改造点：

- 在监测扫描阶段计算学校相关性。
- 输出相关性分、匹配依据和排除原因。
- 线索转换时保留相关性依据。
- 监测信息页展示“为什么判定和本校有关”。

建议字段：

- `school_relevance_score`
- `school_relevance_reason`
- `matched_school_terms`
- `excluded_reason`

第一版规则：

- 命中学校全称、简称、别名，加分。
- 命中校区、学院、部门、地标，加分。
- 命中城市/区县且同时命中学校简称，加分。
- 命中排除词，降分或阻断。
- 只命中泛词、未命中学校上下文，不进入高相关。

涉及范围：

- 后端新增服务：建议放在 `service/campus/judgment` 或 `service/impl/campus` 下，例如 `CampusSchoolRelevanceService`。
- 数据模型：`campus_monitor_result`、`campus_clue` 视实现补字段。
- 前端：`MonitorView.vue` 详情弹窗、监测信息列表。

验收标准：

- 每条监测命中可以看到相关性分和原因。
- 明显无关的同名内容不会进入高风险预警。
- 相关性计算失败不影响原有监测运行。

### 4.3 P2-3 主题分类

现状：

- 事件有 `eventType`。
- 线索和监测命中没有稳定主题字段。
- 前端主题分析更多依赖关键词临时统计。

改造点：

- 在监测命中或转线索时生成主题分类。
- 主题分类来源：规则优先，AI 辅助。
- 事件创建时默认继承线索主题，但允许人工修改。

建议字段：

- `topic_category`
- `topic_sub_category`
- `topic_reason`

规则示例：

- 命中“食堂、饭菜、腹泻、异物、食品安全” -> `food_safety`
- 命中“宿舍、寝室、空调、热水、门禁” -> `dormitory`
- 命中“老师、教师、辱骂、体罚、师德” -> `teacher_ethics`

验收标准：

- 线索列表、监测信息、事件列表均可按主题筛选。
- 主题统计和列表查询使用同一筛选口径。
- AI 分类不可用时规则分类可回退。

### 4.4 P2-4 结构化预警依据

现状：

- `CampusAlert` 有 `matchedKeywords`。
- `CampusAlertServiceImpl` 可以按敏感词和规则生成预警。
- 预警详情对“为什么触发”解释不足。

改造点：

- 为预警增加结构化 evidence。
- 记录命中词类型、风险等级来源、相关性、传播指标、AI 建议。
- 前端预警详情展示依据而不是只展示标题和关键词。

建议第一版字段：

- `evidence_json`

示例：

```json
{
  "riskLevel": "major",
  "riskReasons": ["命中食品安全风险词", "互动数超过阈值"],
  "matchedRiskWords": ["腹泻", "食堂"],
  "schoolRelevanceScore": 86,
  "topicCategory": "food_safety",
  "sourcePlatform": "weibo",
  "metrics": {
    "commentCount": 120,
    "shareCount": 30
  }
}
```

验收标准：

- 每条自动预警都有可读依据。
- 人工创建预警也能填写处理依据或备注。
- 同一来源对象重复预警仍按现有去重逻辑避免刷屏。

## 5. 阶段三：事件处置闭环增强

阶段目标：把“发现风险”升级为“组织处理并可追踪”。

### 5.1 P3-1 状态前置校验

现状：

- 事件已有定级、派单、反馈、退回、复核、归档接口。
- 状态机文档已写明允许流转。
- 文档中已标注后续应补更严格状态前置校验。

改造点：

- 在 `CampusEventServiceImpl` 中集中校验事件和处置任务状态。
- 阻止未定级直接派单、未反馈直接复核、未复核直接归档等非法流转。
- 错误信息使用业务可读中文。

验收标准：

- 非法状态流转返回明确失败。
- 合法流转不受影响。
- 归档事件不可继续派单、反馈或修改状态。

### 5.2 P3-2 相似线索聚合和合并

现状：

- 已有 `CampusEventClue` 关系和线索转事件能力。
- 前端已有“加入事件”的操作痕迹。
- 缺少自动推荐相似线索或事件合并建议。

改造点：

- 线索转事件时，推荐近 7 天相似线索。
- 事件详情页展示“可合并线索”。
- 支持把多条线索批量加入同一事件。

第一版相似规则：

- 同一主题。
- 同一风险等级或相邻等级。
- 近 7 天。
- 标题/正文关键词重合。
- 命中相同学校相关词或风险词。

验收标准：

- 创建事件时能看到相似线索建议。
- 多条线索加入事件后，线索状态更新为 `converted`。
- 同一线索不能重复加入同一事件。

### 5.3 P3-3 SLA 和超时提醒

现状：

- `CampusDisposalTask` 已有 `dueTime`。
- 工作台已有待处理预警、处置中事件等概览。
- 缺少按风险等级自动计算时限和超时标识。

改造点：

- 按风险等级自动建议 `dueTime`。
- 列表和详情展示是否超时。
- 工作台统计超期处置任务。

建议 SLA：

- `concern`：4 小时初核。
- `major`：1 小时响应。
- `urgent`：立即响应，默认 30 分钟内反馈。

验收标准：

- 派单时自动带出建议截止时间。
- 超时任务在事件页、工作台可见。
- 已归档或已确认任务不再计入超时。

### 5.4 P3-4 处置记录产品化

现状：

- 处置记录已有 `recordType`、`recordContent`、`handlerName`、`attachmentDesc`。
- 前端可以反馈、退回、复核。

改造点：

- 事件详情页按时间线展示全部处置记录。
- 记录类型标准化：`assign`、`feedback`、`return`、`confirm`、`archive`。
- 归档时要求填写处置结论。

验收标准：

- 事件详情能完整还原处理过程。
- 处置记录不可静默覆盖。
- 归档结论进入报告复盘数据源。

## 6. 阶段四：报告复盘与治理分析

阶段目标：把“处理单个事件”升级为“发现治理问题”。

### 6.1 P4-1 报告数据源收口

现状：

- `CampusReportController` 已支持模板、报告保存、生成、AI 生成和导出。
- 报告可关联 `eventId`。
- 报告数据源与事件处置记录、预警、线索之间的组织仍需加强。

改造点：

- 明确报告只读取线索、预警、事件和处置记录。
- 日报/周报读取统计数据。
- 事件报告读取单事件详情、线索、处置记录、预警信息。

验收标准：

- 报告不直接读取未研判的宽泛接入记录。
- 事件报告能包含处置时间线。
- 日报/周报能包含新增线索、预警、事件和超时处置统计。

### 6.2 P4-2 报告模板体系

现状：

- 报告模板已存在。
- 前端提供模板编辑和变量插入。

改造点：

- 固化四类模板：
  - 日报
  - 周报
  - 专题报告
  - 重大事件复盘
- 每类模板定义标准变量。

重大事件复盘模板建议结构：

```text
一、事件概况
二、发现与传播过程
三、风险研判依据
四、处置过程
五、处置结果
六、问题复盘
七、整改建议
```

验收标准：

- 新建报告时能选择标准模板。
- AI 生成内容可人工编辑后归档。
- 模板变量缺失时有可读兜底，不输出空洞占位符。

### 6.3 P4-3 治理指标看板

现状：

- 工作台和态势页已有线索、预警、事件、趋势统计。
- 仍偏运营概览，治理复盘指标不足。

改造点：

- 增加治理指标：
  - 高频问题排行。
  - 部门响应效率。
  - 主题风险趋势。
  - 校区/学院风险分布。
  - 重复问题趋势。
  - 超时处置任务。
  - 已处置/未处置比例。

验收标准：

- 管理层能按时间范围查看治理指标。
- 指标能跳转到对应线索、预警或事件列表。
- 统计口径和列表查询口径一致。

### 6.4 P4-4 AI 报告和复盘增强

现状：

- AI 报告生成已接入 `campus_ai`。
- AI 调用日志和失败回退已有基础。

改造点：

- 为日报、周报、事件复盘分别配置 prompt 模板。
- AI 输入只传脱敏摘要、统计数据和处置记录摘要。
- AI 输出必须进入草稿，人工确认后才归档。

验收标准：

- AI 不可用时仍可用传统模板生成报告。
- AI 报告可追溯调用日志。
- 报告归档前必须人工确认。

## 9. 风险与待确认事项

1. 是否需要数据库字段承接学校相关性和主题分类，建议 Batch 41 前确认。
2. 风险等级展示名称是否采用“普通关注/一般预警/重大预警/特别重大”，建议与用户或学校侧确认。
3. SLA 时限是否按学校制度配置，建议做成字典或规则配置，不硬编码。
4. 事件合并是否允许自动合并，建议第一版只做推荐，人工确认后合并。
5. AI 输出是否允许进入预警依据，建议只能作为辅助依据，不能作为唯一触发原因。

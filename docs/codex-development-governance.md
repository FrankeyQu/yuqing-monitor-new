# Codex 全流程开发治理规范

## 1. 目的

本规范用于约束本项目后续使用 Codex 进行全流程开发时的工作方式。主线程负责需求拆解、架构控制、任务分派、代码审查、集成验收；子线程只负责明确边界内的探索、实现或验证任务，不能自行扩大范围。

目标是保证开发过程可控、可审计、可回滚，避免一次性大改、跨模块乱改、数据库迁移失控、合规边界模糊等问题。

## 2. 总体原则

### 2.1 主线程统一控盘

所有需求先由主线程分析、拆分和确认开发顺序。子线程不得直接决定系统架构、数据模型、权限模型和合规边界。

### 2.2 小步开发

每个任务只完成一个清晰目标，例如：

- 只做表结构
- 只做 Mapper/Service
- 只做 Controller 接口
- 只做页面
- 只做审计接入
- 只做测试或修复

禁止一次任务同时完成多个大模块。

### 2.3 先读代码再动手

开发前必须先阅读现有代码结构、命名方式、包路径、Mapper 风格、页面风格和已有权限逻辑。不得凭空创建一套与现有项目不一致的新体系。

### 2.4 主系统优先

本项目第一阶段优先补齐基础能力：

- 组织机构
- 用户权限
- 数据字典
- 审计日志
- 线索库
- 重点关注账号库
- 舆情事件库
- 处置流转
- 基础统计
- 报告归档

爬虫、智能分析、多 Agent、自动报告放到第二阶段。

### 2.5 合规边界优先

重点关注账号功能必须坚持：

- 只处理公开信息、授权数据、上级移交数据、学校业务部门依法依规提供的数据。
- 不处理密码、私信、通讯录、非公开内容。
- 不设计绕过平台限制、破解登录、批量撞库等能力。
- 不做无依据的自动识别学生私人账号。
- 账号入库必须记录来源依据、任务编号、授权范围、关注期限、经办人、审核人。

## 3. 主线程职责

主线程是唯一的项目控盘者，负责：

1. 理解用户需求。
2. 判断是否需要先分析代码。
3. 拆分开发阶段和任务边界。
4. 指定每个子线程的职责、读写范围和交付物。
5. 控制数据库迁移顺序。
6. 控制权限、审计、合规边界。
7. 审查子线程结果。
8. 合并或修正代码。
9. 运行测试或说明无法测试的原因。
10. 向用户汇报改动、风险和下一步。

主线程必须避免：

- 把架构决策交给子线程。
- 让多个子线程修改同一批文件。
- 不看 diff 就接受子线程结果。
- 未确认数据库影响就改旧迁移脚本。
- 为了速度跳过权限、审计和合规字段。

## 4. 子线程类型

### 4.1 探索子线程

用途：

- 阅读代码
- 查找已有实现
- 分析模块结构
- 总结可复用模式

权限：

- 只读
- 不改代码

交付物：

- 相关文件路径
- 现有实现方式
- 建议新增位置
- 可能风险

### 4.2 实施子线程

用途：

- 在明确文件范围内实现功能
- 新增表、接口、Service、页面或测试

权限：

- 只能修改主线程指定的文件或模块
- 不得重构无关代码
- 不得改动其他子线程负责的文件

交付物：

- 修改文件列表
- 核心实现说明
- 自测结果
- 未完成项和风险

### 4.3 验证子线程

用途：

- 运行测试
- 检查接口
- 检查页面
- 检查 SQL
- 做代码审查

权限：

- 默认只读
- 如需修复，必须由主线程重新授权

交付物：

- 测试命令
- 测试结果
- 问题列表
- 建议修复方式

## 5. 子线程任务单模板

主线程给子线程分配任务时，应使用以下结构：

```text
任务名称：

背景：

目标：

允许读取范围：

允许修改范围：

禁止事项：

必须遵循的现有风格：

交付物：

验证要求：
```

示例：

```text
任务名称：实现线索库 Mapper 和 Service

背景：
项目正在建设校园舆情线索库，数据库表已由主线程创建。

目标：
实现线索新增、列表、详情、研判、归档的 Mapper 和 Service。

允许读取范围：
src/main/java/com/stonedt/intelligence/**/*
src/main/resources/mapper/**/*

允许修改范围：
src/main/java/com/stonedt/intelligence/entity/campus/**/*
src/main/java/com/stonedt/intelligence/dao/campus/**/*
src/main/java/com/stonedt/intelligence/service/campus/**/*
src/main/resources/mapper/campus/**/*

禁止事项：
不得修改登录、拦截器、已有监测模块、旧 SQL 迁移脚本。

必须遵循的现有风格：
沿用当前项目 MyBatis XML、Service、Controller 的命名和返回结构。

交付物：
修改文件列表、接口说明、自测结果。

验证要求：
至少检查 Mapper XML 字段和实体字段一致。
```

## 6. 开发流程规范

### 6.1 每个功能的标准流程

```mermaid
flowchart LR
    A["需求输入"] --> B["主线程分析"]
    B --> C["方案打磨"]
    C --> D["读取现有代码"]
    D --> E["拆分任务"]
    E --> F["必要时分派子线程"]
    F --> G["子线程交付"]
    G --> H["主线程审查 diff"]
    H --> I["主线程集成修正"]
    I --> J["运行测试/检查"]
    J --> K["用户验收说明"]
```

### 6.1.1 方案先行规则

从 Batch 21 起，任何新 Batch 或较大功能模块都必须先形成详细实施方案。主线程不得在方案未形成、未自审前直接编码。

方案至少包含：

- 本批目标和明确不做的范围。
- 业务流程、数据流和系统边界。
- 数据库变更、后端接口、前端页面、脚本和文档拆分。
- 权限、审计、合规边界。
- 幂等、去重、失败重试、回滚方案。
- 验收步骤和风险清单。

方案进入 `Plan Review` 后才能继续打磨；涉及真实外部数据源、账号、密钥、合规边界时，必须等用户确认后再进入实现。

### 6.2 每次开发前检查

必须执行或确认：

- 当前分支
- `git status`
- 是否存在用户未提交改动
- 是否涉及数据库迁移
- 是否涉及权限或审计
- 是否涉及敏感数据或账号关注

### 6.3 每次开发后检查

必须执行或说明：

- `git diff` 核心变化
- 修改文件列表
- 编译或测试结果
- 无法测试的原因
- 手工验收步骤
- 可能风险

## 7. Git 使用规范

### 7.1 分支建议

按模块建立分支：

```text
feature/campus-base
feature/campus-clue
feature/campus-account
feature/campus-event
feature/campus-disposal
feature/campus-alert
feature/campus-report
```

### 7.2 提交粒度

推荐一个提交只包含一个主题：

- 新增线索库表结构
- 实现线索库后端接口
- 实现线索库页面
- 接入线索库审计日志
- 修复线索库导入校验

### 7.3 禁止操作

除非用户明确要求，否则禁止：

- `git reset --hard`
- `git checkout -- .`
- 删除用户未提交改动
- 批量格式化无关文件
- 修改历史迁移脚本

## 8. 数据库规范

### 8.1 Flyway 迁移

只新增迁移文件，不随意修改旧迁移。

建议顺序：

```text
V1.1__CampusBaseTables.sql
V1.2__CampusClueTables.sql
V1.3__CampusAccountTables.sql
V1.4__CampusEventWorkflowTables.sql
V1.5__CampusAlertAndReportTables.sql
```

### 8.2 表设计要求

核心业务表必须包含：

- 主键
- 创建时间
- 更新时间
- 创建人
- 更新人
- 状态字段
- 逻辑删除字段，如项目已有类似规范则沿用

涉及重点关注账号的表必须包含：

- 来源依据
- 任务编号
- 授权范围
- 关注开始时间
- 关注结束时间
- 审核人
- 审核时间
- 责任部门

### 8.3 SQL 安全

禁止：

- 拼接未过滤 SQL
- 无分页大查询
- 无条件批量删除
- 直接物理删除关键业务数据

## 9. 权限与审计规范

### 9.1 权限控制

每个新模块必须考虑：

- 菜单权限
- 按钮权限
- 数据范围权限
- 导入权限
- 导出权限
- 审计查看权限

### 9.2 审计覆盖

以下操作必须记录审计日志：

- 登录
- 查看敏感详情
- 新增线索
- 导入线索
- 研判线索
- 账号入库
- 账号审核
- 事件定级
- 任务分派
- 处置反馈
- 报告生成
- 报告下载
- 权限变更
- 数据导出

### 9.3 审计字段

审计日志至少包含：

- 操作人
- 操作人部门
- 操作时间
- 操作 IP
- 操作类型
- 操作对象
- 对象 ID
- 请求参数摘要
- 操作结果
- 失败原因

## 10. 安全规范

### 10.1 配置安全

禁止提交：

- 真实数据库密码
- Redis 密码
- JWT 密钥
- 模型 API Key
- 采集账号 Cookie
- 生产环境地址

### 10.2 默认账号

必须替换：

- 默认管理员账号
- 默认密码
- 默认密钥
- 示例数据库密码

### 10.3 文件安全

上传文件必须限制：

- 文件类型
- 文件大小
- 存储路径
- 下载权限

禁止把任意系统目录暴露为静态资源。

## 11. 页面开发规范

页面应以业务效率为核心，不做花哨营销式页面。

优先采用：

- 列表
- 筛选
- 详情
- 表单
- 状态流转
- 操作按钮
- 确认弹窗
- 导入导出

关键页面必须体现：

- 风险等级
- 当前状态
- 责任部门
- 办理时限
- 最新处置进展
- 审计留痕入口

## 12. 测试与验收规范

### 12.1 后端检查

优先执行：

```text
mvn test
mvn package -DskipTests
```

如果本地缺 JDK/Maven/MySQL/Redis，必须说明无法执行的原因。

### 12.2 前端检查

优先执行：

```text
npm install
npm run build
```

如存在依赖漏洞或构建失败，必须记录。

### 12.3 手工验收

每个模块完成后必须给出手工验收步骤，例如：

1. 使用管理员登录。
2. 进入线索库。
3. 新增一条线索。
4. 执行研判。
5. 转为事件。
6. 查看审计日志。

## 13. 子线程结果审查清单

主线程接收子线程结果后，必须检查：

- 是否超出允许修改范围
- 是否修改了无关文件
- 是否遵循现有代码风格
- 是否引入硬编码密钥
- 是否破坏旧接口
- 是否新增必要权限
- 是否记录必要审计
- SQL 是否可重复执行
- 是否存在空指针或分页问题
- 是否有测试或手工验证说明

审查不通过时，主线程应选择：

- 局部修正
- 要求子线程返工
- 丢弃该子线程结果
- 拆成更小任务重新做

## 14. 推荐开发顺序

```text
0. 环境跑通与安全整改
1. 组织机构、字典、权限、审计基础
2. 线索库
3. 重点关注账号库
4. 舆情事件库
5. 处置流转
6. 预警规则
7. 统计分析与大屏
8. 报告归档
9. 数据接入服务
10. 智能分析服务
11. 自动报告服务
```

## 15. 主线程执行口径

后续用户提出开发任务时，主线程默认按以下口径执行：

1. 先判断任务属于哪个阶段。
2. 先读相关代码，再决定改法。
3. 优先做最小可交付闭环。
4. 涉及子线程时先明确读写范围。
5. 子线程只做局部任务。
6. 主线程统一审查、集成和验收。
7. 最终汇报修改内容、测试结果和风险。

本规范作为本项目 Codex 开发过程的默认约束。除非用户明确要求变更，否则后续开发应遵循本规范。

## 16. Batch 11-20 主线程控盘规则

从 Batch 11 起，主线程需要持续监控并决策到 Batch 20 完成。

详细控制台见：

```text
docs/codex-main-thread-control-board.md
```

主线程默认负责：

- 判断下一批开发顺序。
- 拆分任务和验收口径。
- 控制检测引擎、新前端、权限、大屏、验收之间的依赖。
- 每批完成后更新控制台。
- 遇到编译、启动、迁移、接口、页面问题时先主动修复。
- 只有涉及产品方向、合规边界、真实数据接入、不可逆操作时再请求用户确认。

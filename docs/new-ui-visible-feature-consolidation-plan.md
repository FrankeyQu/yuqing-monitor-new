# 新版页面可见功能收口方案

## 工作分支与 Worktree

- 工作分支：`claude/batch33-monitor-admin`
- 当前 worktree：`D:\PRJ\yuqing`
- 远端跟踪分支：`deploy-vps/claude/batch33-monitor-admin`
- 本次工作性质：只保存方案文档，不修改业务代码、不新增接口、不执行迁移
- 未使用的其他 worktree：`D:\PRJ\yuqing-daily-monthly-reports`（分支 `claude/daily-monthly-reports`）

## 背景与目标

本方案只针对新版页面里客户实际看得到、点得到的功能做收口，不把旧页面、旧 Controller 或不可达页面当作客户可见功能重复。目标是让新版页面达到“显示即有效”：可见选项能真实生效，可见按钮语义清楚，可见导航符合权限，不再把预留能力暴露给客户。

## 1. 监测页筛选与排序收口

### 1.1 相似信息

当前问题：

- 前端有“相似信息”开关，并会传 `similarDedup=true`。
- 线索查询已有类似去重 SQL，但监测信息查询没有使用该参数。
- 客户开启后看不到真实效果，属于“显示了但没生效”。

解决方案：

- 将前端文案从“相似信息”改成“合并相似信息”，明确语义是列表去重展示。
- 默认关闭，避免客户误以为数据减少。
- 后端在 `/campus/monitor/information/list`、平台统计、子平台统计里统一应用同一去重口径。
- 去重优先级：
  1. 优先按接入记录 `content_hash` 去重。
  2. 没有 `content_hash` 时按有效原文链接去重。
  3. 再没有链接时按“标题 + 平台”去重。
- 每组相似内容只展示最新一条，排序依据为 `info_time DESC, info_id DESC`。
- 不删除任何监测结果，只影响列表展示、分页总数和统计口径。

影响评估：

- 不需要新增表。
- 不影响监测结果原始数据。
- 可能导致开启去重后总数减少，这是预期行为，需要用“合并相似信息”文案解释。

### 1.2 价值度、网站等级排序

当前问题：

- 新版监测页展示“价值度”“网站等级”排序。
- 后端监测信息查询实际没有对应排序逻辑。
- 当前系统也没有稳定的价值度/网站等级字段定义。

解决方案：

- 从新版页面删除“价值度”“网站等级”排序选项。
- 默认排序改为“采集时间”。
- 保留排序项：
  - 采集时间：`infoTime`
  - 发布时间：`publishTime`
  - 相关度：`relevance`
  - 情感：`sentiment`
- 后端继续兼容旧请求里的 `value`、`siteLevel`，统一落到默认排序，避免历史调用报错。
- 文档中不再把 `value/siteLevel` 作为推荐参数。

影响评估：

- 对客户是正向收口，减少无效选项。
- 不影响真实业务能力。
- 不需要数据库调整。

### 1.3 情感识别口径

当前问题：

- 前端筛选展示“疑似正面/确认正面/疑似中性/确认中性/疑似负面/确认负面”。
- 后端监测结果主要使用 `positive/neutral/negative`，也兼容部分中文值。
- “疑似/确认”更像研判确认状态，不适合作为情感分类。

统一口径：

- 数据库存储推荐值：
  - `positive`：正面
  - `neutral`：中性
  - `negative`：负面
  - 空值或 `none`：未知
- 前端展示值：
  - 正面
  - 中性
  - 负面
  - 未知
- 前端筛选项：
  - 全部
  - 正面
  - 中性
  - 负面
  - 未知

实施方案：

- 监测页删除“疑似/确认”情感筛选。
- 新增统一情感工具函数，前端展示、筛选、表单都复用同一映射。
- 后端查询兼容历史值：
  - `疑似负面/确认负面/负面/negative` 归为负面。
  - `疑似中性/确认中性/中性/neutral` 归为中性。
  - `疑似正面/确认正面/正面/positive` 归为正面。
- 新增一次迁移，把历史中文情感值规范化为英文枚举。
- “疑似/确认”以后放到研判状态表达：待研判表示未确认，已研判表示人工确认。

影响评估：

- 报告、教育专题、对比分析等统计会更稳定。
- 需要同步检查 RuleJudgmentEngine 和 AiJudgmentEngine，避免继续写入“疑似负面/疑似中性”等情感值。
- 这是口径修正，不是功能下线。

## 2. 添加文章与新增线索合并

当前问题：

- 监测页同时有“添加文章”和“新增线索”。
- “添加文章”实际也是保存 `CampusClue`，只是字段更少。
- 客户容易误以为“添加文章”会新增一条监测命中，但它不会进入普通监测结果列表。

是否可以合并：

- 可以合并。
- 当前“添加文章”没有独立后端语义，本质是低配版线索新增。
- 合并后不影响监测结果“转线索”流程。

解决方案：

- 删除“添加文章”按钮和弹窗。
- 保留一个入口，命名为“新增人工线索”。
- 原“新增线索”弹窗标题改为“新增人工线索”。
- 默认 `clueSource=manual`。
- 保存成功提示改为“人工线索已新增”。
- 在监测页中明确：自动命中的内容通过“转线索”进入线索体系，人工补录内容通过“新增人工线索”进入线索体系。

影响评估：

- 不需要新增 API。
- 不影响已有线索保存逻辑。
- 减少一个重复入口，客户操作更清楚。

## 3. 批量操作彻底收口

当前问题：

- 监测信息列表里既有普通监测命中，也有已转线索的数据。
- 当前批量操作只对有 `clueId` 的行有效。
- 客户勾选普通监测结果时，会出现“选了但不能处理”的割裂感。

解决方案：

- 选中数据后分两类统计：
  - 监测命中：有 `monitorResultId` 的行。
  - 已转线索：有 `clueId` 的行。
- 批量动作按对象类型拆清楚：
  - 监测命中支持：批量转线索、批量转预警、批量忽略。
  - 已转线索支持：批量研判、批量加入事件。
- 混合选择时，动作按钮显示可处理数量。
- 不适用的动作禁用，并给出原因。
- 执行结果必须展示成功、失败、跳过数量。
- 不允许再静默忽略选中项。

影响评估：

- 需要补前端交互和批量执行逻辑。
- 后端可先复用现有单条接口循环执行，不必第一版新增批量 API。
- 如果后续数据量较大，再补真正的批量 API。

## 4. 数据接入页面暂时隐藏

当前要求：

- 数据接入页面暂时不展示给客户。
- 后端接入能力保留。

解决方案：

- 后台导航移除“数据接入”。
- `/admin/ingest` 直接访问时重定向到 `/admin/monitor-tasks`。
- 后端菜单种子增加迁移，把数据接入菜单设为不可见。
- 主侧边栏继续过滤 `/ingest` 和 `/admin/ingest`。
- 保留 `IngestView.vue`、接入 Service、接入 Controller 和接入表结构，作为内部能力和监测任务自动接入能力使用。
- 文档同步说明：数据接入是后端保留能力，客户页面暂不展示。

影响评估：

- 客户不会看到未验收的接入配置项。
- 不影响监测任务自动绑定和运行接入任务。
- 不删除接口，避免影响内部运维和后续恢复。

## 5. 权限与导航完善

当前问题：

- 前端登录态主要依赖 localStorage。
- 后台导航在权限加载失败或过滤为空时可能回退展示全部菜单。
- 主侧边栏固定显示“后台管理”，没有按权限隐藏。

解决方案：

- 路由进入受保护页面前，调用 `/campus/system/current-user` 校验真实 session。
- 校验失败时清理 localStorage 并跳转登录页。
- 后台导航不再 fallback 到全部菜单。
- 权限加载失败时展示空菜单或提示“暂无后台权限”。
- 没有后台菜单权限的用户，主侧边栏隐藏“后台管理”。
- `/admin/**` 路由增加前端权限判断：
  - 有权限时进入目标页。
  - 无权限时进入第一个有权限的后台页。
  - 完全无后台权限时跳回首页。
- 后端 `CampusPermissionInterceptor` 保持最终拦截，不依赖前端做安全边界。

影响评估：

- 客户看到的菜单会更准确。
- session 过期时跳转更及时。
- 不改变后端权限模型，只改善前端展示和路由体验。

## 验收测试

- 监测页开启/关闭“合并相似信息”，确认列表、分页、平台统计口径一致变化。
- 排序只展示采集时间、发布时间、相关度、情感，且每项真实生效。
- 情感筛选只展示全部、正面、中性、负面、未知，且与列表徽标和统计一致。
- “新增人工线索”能保存，且不会被误认为新增普通监测命中。
- 监测命中批量转线索、转预警、忽略可用。
- 已转线索批量研判、加入事件可用。
- 混合勾选时无静默忽略，结果显示成功、失败、跳过数量。
- 客户账号看不到“数据接入”。
- 直接访问 `/admin/ingest` 会被重定向。
- 没有后台权限的账号看不到“后台管理”。
- session 过期后刷新页面会跳转登录页。

最低门禁：

- `campus-web npm run build`
- `.\mvnw.cmd -DskipTests compile`

## 默认假设

- 数据接入只是客户页面暂时隐藏，不下线后端能力。
- “疑似/确认”以后不再作为情感分类，而由研判状态表达。
- 本方案不处理旧页面不可达代码，也不删除历史兼容 API。
